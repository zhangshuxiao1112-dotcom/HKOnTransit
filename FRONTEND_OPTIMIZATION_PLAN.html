HKOnTransit Frontend Optimization Plan

A passenger-focused journey companion with official data, explicit source labels and an optional language interpretation layer.

This English document describes the original v2 design direction and the current delivery boundary. Proposed features below are not claims of completed functionality.

1. Audit and gaps

The application uses a FastAPI gateway for GMB, KMB, Citybus, MTR and HKO. The single-page interface uses plain HTML, CSS and JavaScript, with SQLite storing fresh ETA snapshots.

  • Journey comparison contains sample itineraries, not an arbitrary multimodal route search.
  • Community reports stay within the current page and are unverified.
  • ETA correction requires independently observed arrivals before publishing accuracy results.
  • Accessibility preferences do not establish facility availability or book operator assistance.

2. Design principles

  • Keep primary travel tasks quick and readable, without obstructing navigation or arrivals.
  • Use one continuous workflow: Plan, Board, Ride and Arrive.
  • Identify official information, unverified observations and unknown conditions separately.
  • Help passengers identify the stop and direction and understand when to request alighting.
  • Use AI for language interpretation and explanation. Official sources and deterministic rules govern transport facts.

3. Information architecture

  • Plan: enter preferences and inspect a sample journey.
  • Board: select an operator, route, direction and stop; inspect official ETA and coordinates.
  • Ride: manually advance through a stop sequence to preview reminders.
  • Arrive: future work on verified walking connections and transfer discount eligibility.

4. Hybrid AI architecture

The model produces structured candidates. Schemas and transport rules validate them before use. Frequent ETA, stop and map operations do not call an LLM. Structured AI output is cached separately.

  • Preference interpretation maps language to a fixed preference enum, weights and quick-choice IDs.
  • Report structuring extracts a mobility event while retaining an unverified status.
  • Route explanation describes supplied route data without inventing fares, arrival times or stops.

The default adapter uses local keyword rules. DeepSeek requires credentials and has a bounded fallback. The model identifier is configurable; a credentialed live model was not validated in this delivery.

5. API contracts

  • POST /api/ai/interpret-preferences: natural-language preferences to validated intent.
  • POST /api/ai/structure-report: an observation to an unverified mobility event.
  • POST /api/ai/explain-route: supplied route data to an explanation.
  • GET /api/ai/status: configured provider and fallback information.

The report and explanation JavaScript hooks remain reserved integration points; they do not implement a live route engine or shared reporting system.

6. Frontend modules

  • index.html: screens, responsive styles and local UI interactions.
  • static/live.js: official lookup, arrival rendering and progressive stop-name loading.
  • static/network.js: bounded same-origin requests and recovery messages.
  • static/ai.js: preference interpretation and optional AI hooks.
  • static/connections.js: five-provider diagnostics.
  • static/i18n.js: compatibility hooks for this English-only release.

Potential future work includes extracting shared styles and screen modules. A large framework is not required for this prototype.

7. Screen guidance

  • Home: concise preferences and a clear distinction between live lookup and sample planning.
  • Results: label illustrative durations; verify routes, direction, payment and transfer windows before claiming discounts.
  • Boarding: show official timestamps, direction and coordinates; retain unverified photo and capacity states.
  • Ride: label manual progression and explain that reminders are not actual vehicle tracking.
  • Reports: distinguish observation time from submission time and make the local-only review state clear.
  • Accessibility: separate Confirmed, Not Accessible and Unknown states.

8. Inclusive interaction

Use readable controls, large text, keyboard focus, screen-reader labels and optional speech. Text and icons accompany status colours. User testing with passengers remains future work; the presence of toggles is not evidence that accessibility needs have been resolved.

9. Evidence and transparency

ETA Lab shows snapshot and independent observation counts. MAE, the proportion within three minutes and prediction interval coverage require a defined observed-arrival dataset and hold-out evaluation. Do not publish invented improvement figures.

10. Delivery phases

  • Implemented: official lookup adapters, English interface, AI schemas/adapters, local preference interpretation, bounded requests, diagnostics and an IDLE-compatible launcher.
  • Planned: further screen modularisation, grounded explanations integrated with real routing, shared report moderation, verified transfer rules, and independent ETA correction evaluation.
  • Requires external setup: credentialed AI validation and production hosting.

11. Risks and responses

  • Model hallucination: constrain outputs and validate schemas; retain official transport values.
  • Unverified observations: explicit review status and no automatic official-data overrides.
  • Slow services: deadlines, selective retry, cached responses and failure circuits.
  • Provider changes: isolate adapters and keep model configuration separate from business logic.
  • Insufficient evidence: retain official baselines and withhold accuracy claims until evaluated.
